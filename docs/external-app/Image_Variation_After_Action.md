## Current corrective workflow

1. Read the current GitHub job and each complete article. Identify its visual thesis, distinctive facts and mechanism.
2. Before generating, reserve six article-appropriate compositions, palette families, hierarchies and annotation approaches.
3. Use the completed five-Brief calibration or a bounded operator-only historical sample to understand variation. Do not copy previous imagery or repeat broad archive research for each story.
4. Generate and review one image at a time. Record article alignment, mechanism depth, mandatory text, palette and composition before starting the next story. Recover any pending candidate before allocating a duplicate attempt.
5. Compare each new candidate with earlier accepted visual signatures at the operator/reviewer level. Pass only the new story's content and its own visual assignment into the generator.
6. Save the actual signature and image hash after acceptance. Preserve successful work through interruptions and reuse unaffected passing images. If later review identifies a real defect in an accepted candidate, create and review a versioned successor with an explicit supersedes record; preserve the old bytes/history. Transfer failures alone do not justify regeneration.
7. Inspect the final six saved images as a set and record visible differences. Different hashes or differently named signatures are not sufficient evidence of visual diversity.

8. Correct every failed image or set-level requirement and repeat individual and set reviews until all six pass. The executing session owns these corrections; no fixed quality-attempt cap or routine owner intervention ends that responsibility. Actual unavailable-tool, quota, access or source-data blockers leave the assignment incomplete with a durable resume checkpoint.
9. Upload all six final passing PNGs and the matching manifest/review records to the job's GitHub staging paths, then verify the exact committed bytes by readback. This is an intermediate checkpoint. Continue through the protected image-only release and verify all six live images in the dated Brief and correct permanent articles. **Completion requires 6/6 review passes, 6/6 verified GitHub readbacks and 6/6 verified live publications.** Local files, staged packages and review-only reports are incomplete.

| Training, adoption or organizational process | Supported progression, timeline or comparison |
| Quantitative or categorical relationships | Source-grounded infographic or hybrid editorial diagram |

These are possibilities, not instructions to insert unsupported objects or architecture. An **infographic-like look is allowed when it helps the specific article**. Keep it explanatory, detailed, readable and professional. Do not turn all six into one infographic template or add invented data for visual balance.

## Reconciled six-image targets

Use the stronger six-composition requirement from the Perfect Image specification, supplemented by the palette and repetition controls from this after-action:

- Six distinct composition signatures.
- At least four layouts, four diagram grammars and four hierarchy patterns.
- At least three annotation patterns.
- At least four dominant palette families and four mechanism metaphors.
- No more than two images with the same primary grammar.
- No more than two generic input–engine–output arrangements.

Retain one white-background professional editorial standard. Vary the actual palette balance, major objects, perspective, connectors, reading path and evidence representation when the article supports it. Do not use alternate field names to count the same visual structure twice. If a target conflicts with faithful explanation, revise the plan or record the unresolved constraint; do not distort the article.

## Visual-signature record

For each image, record: story ID; image SHA-256; composition signature; layout; diagram grammar; dominant palette; mechanism metaphor; major object family; connector treatment; hierarchy; annotation pattern; perspective/depth; evidence representation; supported feedback pattern or “none”; visual-review result; accepted/locked status.

Record an observable explanation for each classification. The signature describes the finished pixels, not only the intended prompt.

## Quality remains mandatory

Use exact **1200 × 630 PNG**, white or near-white, source-faithful explanation, the established 12-component richness target, 3–5 regions, visible internal substages, supported secondary relationships and clear hierarchy. Infographic styling changes presentation, not the quality bar.

**Readable explanatory text is mandatory.** Prepare a nonempty source-supported exact label list. An empty legacy list means preparation is incomplete, not that text is forbidden. No title-only compliance, pseudo-writing, fake paragraphs or illegible labels.

No people/humanoids, logos, photorealistic scenes, invented product behavior, decorative padding or sparse fallback. Count meaningful roles, not repeated props. Inspect actual saved pixels and preserve accepted bytes.

## Evidence required to close the variation issue

The guidance is updated; do not claim the recurring image problem is solved until a real subsequent six-image set demonstrates:

- Pre-generation composition reservations tied to the actual articles.
- Sequential generation with durable reviews and honest attempt records.
- Mandatory readable labels and correct article-specific mechanisms.
- Visible composition, grammar, palette and annotation diversity.
- Individual and set-level saved-pixel review bound to exact hashes.
- Successful six-PNG GitHub return with no regeneration of accepted images for transport failures.

Synthetic tests can verify interface behavior, not visual quality. Keep the historical issue open for outcome verification until this evidence exists.
