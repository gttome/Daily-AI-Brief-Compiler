# D0 Zero-Cost Pre-Proof

Status: required before formal P0-A/P0-B and before D0 activation.

## Decision

There is no paid-capacity branch. D0 may use only native ChatGPT Images already included in the user's ChatGPT subscription. Work, Codex, paid model APIs, paid image APIs/services, billable overage, new paid infrastructure, alternate accounts, owner image upload/manual transfer, and owner-liveness prompts are prohibited.

A temporary native-capacity or supported-tool outage is not a visual failure and is not a reason to weaken D0. Persist the blocker as `BLOCKED_RETRYABLE`, consume zero visual attempts, and retry in a later ordinary Compiler invocation.

## Capability findings

The pre-proof no longer depends on a hypothetical custom persistence plugin.

Current ChatGPT product behavior provides the isolation primitive: a standalone scheduled task starts a new chat for each scheduled run. The live Compiler transport preflight also proved the exact-byte primitive with already-connected tools:

```text
native ChatGPT image
  -> runtime generated file ID
  -> ephemeral Google Drive upload
  -> raw Drive fetch with complete base64
  -> GitHub Git Data blob/tree/commit
  -> exact Git blob readback
  -> delete ephemeral Drive file
```

The transport-only preflight is documented in `docs/D0-NATIVE-BYTE-BRIDGE.md`. It proved native generated-file handoff and byte-for-byte Git persistence without owner transfer or paid capacity. It did not claim clean-session isolation, so P0-A remains independently proven by two standalone scheduled runs.

## Minimum-image strategy

P0-R1 through P0-R5 use **two total disposable native images**.

- Run A and Run B are two different standalone scheduled tasks/new chats.
- Each task contains a conspicuous unrelated outer-context canary.
- The exact image-generator prompt is fetched from one sealed story-only prompt file and submitted explicitly to native ChatGPT Images.
- The canary is in the scheduled-task control context but absent from the exact generator prompt.
- Each run generates exactly one native image.
- Each run captures and persists the exact generated bytes before the run yields, using the proven ephemeral Drive-to-Git bridge.
- The Drive object is deleted after exact Git readback.
- The two story packets, run nonces, scheduled-task identities, and persisted raw byte streams must all be distinct.

The same immutable evidence satisfies R1-R5. After deterministic validation passes, formal P0-A and P0-B are promotions of that evidence and MUST NOT regenerate the two images merely to repeat the experiment.

## P0-R1 — standalone-session primitive

For both runs require:

- `session_boundary.method = standalone_scheduled_task_new_chat`;
- two distinct standalone scheduled-task identities;
- two distinct run nonces;
- the documented product contract that each standalone scheduled run starts a new chat;
- no prior-chat context available in the run;
- no prior images available in the run;
- native executor is ChatGPT Images included in the subscription.

If a standalone scheduled run cannot start because the platform is temporarily unavailable, record `STANDALONE_SCHEDULED_RUN_TEMPORARILY_UNAVAILABLE` and retry later.

## P0-R2 — isolation canaries

Each task's outer control context contains a unique, conspicuous canary. The exact generator prompt is independently hashed and MUST NOT contain that canary.

Evidence requires:

- exact generator prompt SHA-256;
- outer canary present in scheduled-task control context;
- outer canary absent from generator prompt;
- generated image contains no canary element;
- generated image contains no unrelated story, prior-image, repository, run, or orchestration material;
- generated image is materially about its sealed story.

Two materially different packet hashes are mandatory.

This combines a platform fresh-chat boundary with an explicit-prompt canary test; it is stronger than an instruction such as "ignore prior context."

## P0-R3 — native image to runtime file handoff

Immediately after native generation and before the scheduled run yields:

1. capture the runtime-generated native image file ID;
2. upload that exact runtime file to the already-connected Google Drive as a temporary object;
3. require no owner approval or owner action;
4. fetch that temporary file as raw bytes/base64 in the same run;
5. never use owner download/upload, screenshots, re-rendering, reconstruction, later Library selection, or cross-run asset recovery.

A missing generated-file handoff caused by a temporary platform/tool outage is `RUNTIME_GENERATED_FILE_HANDOFF_TEMPORARILY_UNAVAILABLE` and consumes zero image-quality attempts.

## P0-R4 — exact-byte persistence

Using the raw bytes fetched in the same scheduled run:

1. compute or bind byte count and SHA-256;
2. create the Git blob from the complete base64 payload;
3. create tree and commit on the disposable proof branch;
4. compare-and-swap the branch head;
5. read back the persisted Git blob identity;
6. require exact Git blob SHA equality;
7. delete the ephemeral Drive object.

GitHub is the durable system of record. Google Drive is only a same-run byte shuttle.

The repository receipt binds generated file ID, ephemeral file ID, raw byte count, SHA-256, Git blob SHA, immutable proof path, commit SHA, readback PASS, and cleanup PASS.

## P0-R5 — repeatability

Both independent runs must pass R1-R4. Require:

- 2 distinct scheduled-task titles/identities;
- 2 distinct run nonces;
- 2 materially different packet hashes;
- 2 distinct raw byte streams;
- zero canary or unrelated-context leakage;
- zero owner intervention;
- zero paid/prohibited dependencies.

Only then is `daily-compiler-d0-capability-proof-v2` PASS.

## Formal P0-A/P0-B promotion

A validated v2 PASS receipt authorizes formal P0-A and P0-B. Formal receipts bind/restate the immutable pre-proof evidence; they do not require fresh generations. P0-C through P0-F remain separate proof stages.

## Failure semantics

`BLOCKED_RETRYABLE` is allowed only for explicit transient capability codes in the executable validator. It never authorizes P0-A/P0-B and never consumes a visual-quality attempt. There is no timeout that converts a retryable block into paid capacity, Proposal 1R reader-story fallback, owner transfer, same-chat generation, or architecture expansion.

A true `FAIL` is reserved for contradictory evidence: reused task/run identity, actual canary contamination, wrong story, cross-run byte recovery, hash/readback mismatch, or violation of the zero-cost boundary.
