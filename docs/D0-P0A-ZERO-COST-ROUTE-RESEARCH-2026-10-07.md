# D0 P0-A Zero-Cost Native Route Research — 2026-10-07

Status: research complete for the currently exposed ChatGPT product surfaces; D0 remains inactive.

## Objective

Find a zero-added-cost native ChatGPT mechanism that can satisfy **all** P0-A requirements at once:

1. genuinely fresh story-only image-generation context;
2. exact story prompt binding;
3. native ChatGPT Images generation already included in the subscription;
4. programmatic access to the generated result for pixel inspection;
5. exact generated bytes available before the image capsule ends;
6. same-invocation persistence to the Compiler without adding repository/run/orchestration prose to the generator-visible context;
7. unattended invocation with zero owner liveness.

No route may use Work, Codex, paid APIs/services, billable overage, new paid infrastructure, alternate accounts, owner image transfer, or Proposal 1R reader fallback.

## Official product findings

### Standalone Scheduled task

OpenAI documents that standalone scheduled tasks start a new chat for each run and report results in Scheduled. Scheduled tasks can use supported connected apps. This gives a strong fresh-run primitive.

Sources:

- https://learn.chatgpt.com/docs/automations
- https://help.openai.com/en/articles/10291617-scheduled-tasks-in-chatgpt

However, the available Compiler runtime exposes task metadata and notifications, not a task-run result API returning the generated image/file reference. The two pure story-only scheduled proof runs completed, yet no generated result asset became accessible through the available task, Gmail, or Files/Library tool surface. Repeating the same experiment is therefore prohibited by the P0-A no-rework gate.

### ChatGPT Images / Images tab

OpenAI documents that generated images are automatically saved under Images.

Source:

- https://help.openai.com/en/articles/11084440-images-in-chatgpt

The currently exposed Compiler Files/Library tools do not provide unattended access to those Scheduled-run Images-tab assets. A human can browse Images, but owner retrieval is prohibited.

### Temporary Chat

OpenAI documents two modes:

- **Unpersonalized Temporary Chat**: no memory, custom instructions, or plugins.
- **Personalized Temporary Chat**: may use memory, custom instructions, and plugins.

Source:

- https://help.openai.com/en/articles/8914046

Unpersonalized Temporary Chat has the clean boundary but loses the connected persistence tools. Personalized Temporary Chat can use plugins but is not a proven story-only boundary. In addition, the Compiler has no supported unattended primitive for creating and driving a new Temporary Chat.

### Custom GPT

OpenAI documents that GPT conversations do not use saved memory, custom instructions, or previous conversations; each GPT conversation starts fresh. GPTs can be configured with capabilities including image generation and actions.

Source:

- https://help.openai.com/en/articles/8554407-gpts-in-chatgpt

This is architecturally promising for clean isolation, but Scheduled tasks explicitly do not support GPTs. The Compiler therefore has no zero-owner autonomous invocation path for an existing GPT.

### Plugin file handoff

OpenAI's plugin reference documents file inputs with `file_id` and temporary `download_url`, plus anonymized session metadata. This is sufficient for exact-byte persistence **once the generated image file is available to a tool call**.

Source:

- https://developers.openai.com/plugins/reference

The already-completed P0-B proof demonstrates that exact generated bytes can be moved through an already-connected ephemeral Google Drive shuttle into Git with exact readback. The missing capability is not byte transport; it is the clean, autonomous handoff from a pure image-generation capsule to that persistence action.


## Additional zero-cost route checks

### Shared Scheduled-task links

OpenAI's sharing documentation is explicit that a shared task snapshot contains the task title, instructions, schedule, and time zone, but **does not include previous task results**. Completed tasks cannot be newly shared. A shared-task link therefore cannot be used as an unattended extraction path for the existing pure-task image result.

Sources:

- https://help.openai.com/en/articles/10291617-scheduled-tasks-in-chatgpt
- https://help.openai.com/en/articles/7925741-sharing-conversations-and-scheduled-tasks-in-chatgpt

### Team-task Previous runs

OpenAI documents a `Previous runs` UI for team tasks; a user can open a run and inspect its conversation/result. This improves human observability, but the Compiler runtime has no supported task-run-result action that returns that run's generated file or exact image bytes. UI-only access does not satisfy autonomous result visibility.

Source:

- https://help.openai.com/en/articles/20001540-creating-and-managing-team-tasks-in-chatgpt

### Plugin file/library APIs

OpenAI's plugin file APIs are strong once a file ID is already authorized. A plugin can download a file that was uploaded by a widget, selected from the file library, passed through a file parameter, or returned by a tool file reference. Widget state can also preserve authorized image IDs for later turns.

Those APIs do **not** document automatic entitlement to the file ID of a native ChatGPT Images result produced by a separate pure Scheduled run. `selectFiles()` is an interactive file picker, so relying on it would reintroduce owner action.

Sources:

- https://developers.openai.com/plugins/reference
- https://developers.openai.com/plugins/build/chatgpt-ui

### Plugin skills or server instructions as a post-generation hook

ChatGPT now reads MCP server instructions and uses them with tool metadata to understand workflows. A plugin can also package skill instructions. That is useful for workflow orchestration, but it does not create a proof-safe hidden post-generation hook: the instructions are model context, and the current native ChatGPT image surface does not expose a separately auditable caller-supplied image prompt that excludes those instructions.

OpenAI's plugin packaging docs list lifecycle hooks only for manually installed Codex desktop plugins. Codex is prohibited by the Compiler runtime contract, so those hooks are not a route.

Sources:

- https://developers.openai.com/plugins/changelog
- https://developers.openai.com/plugins/concepts/plugins
- https://developers.openai.com/plugins/build/plugins

### Export / Compliance paths

Personal ChatGPT data exports do not include Scheduled tasks. OpenAI states that Scheduled tasks are included in the Enterprise Compliance API, but that does not supply an in-run native-image file handoff and it is not an available zero-cost Compiler runtime primitive.

Sources:

- https://help.openai.com/en/articles/10291617-scheduled-tasks-in-chatgpt
- https://help.openai.com/en/articles/7925741-sharing-conversations-and-scheduled-tasks-in-chatgpt


## Current OpenAI docs recheck — plugin handoff

A fresh documentation recheck narrows the plugin route further.

OpenAI's plugin reference says a plugin may obtain a temporary download URL only for a file ID that is already authorized by one of four paths: widget upload, interactive file-library selection, a tool file parameter, or a tool-result file reference. The documented API does not say that a native ChatGPT Images result from a separate pure Scheduled run is automatically placed into that authorization set.

OpenAI's May 2026 plugin changelog also confirms that ChatGPT reads MCP server instructions and uses them alongside tool metadata. That makes server-wide "after image generation, persist the image" instructions unsuitable as isolation proof by themselves: they are model context, not a demonstrably separate post-generation hook. The current custom-MCP quickstart tests personal MCP plugins through ChatGPT Work, and Work is explicitly outside the Compiler runtime boundary.

Sources:

- https://developers.openai.com/plugins/reference
- https://developers.openai.com/plugins/build/chatgpt-ui
- https://developers.openai.com/plugins/changelog
- https://developers.openai.com/plugins/concepts/mcp-server
- https://developers.openai.com/plugins/quickstart

This does not invalidate the existing P0-B byte bridge. It confirms that the unresolved problem remains the **native result handoff from an isolated pure image-generation context**, not Git persistence or pixel review.

## Research closure

The expanded route matrix now covers the additional plausible native routes above. None currently satisfies all seven P0-A capabilities at the same time. This materially narrows the blocker: **the missing primitive is a supported autonomous boundary that both isolates the native image generator and exposes that exact result file to post-generation persistence without inserting the persistence workflow into generator-visible context.**

Until OpenAI exposes that primitive, D0 stays proof-gated. The correct engineering action is to preserve the completed P0-B/P0-C/P0-D capability evidence and avoid further native generations, not to weaken isolation or introduce a paid/manual path.

## Current conclusion

No currently exposed route satisfies every required capability simultaneously.

This is **not** a request for paid capacity and does not justify architectural fallback. The correct state is:

```text
P0-B exact-byte persistence       PASS
P0-C deterministic normalization PASS
P0-D exact-pixel review mechanism PASS (capability only)
P0-A clean autonomous capsule     BLOCKED
P0-E strict first-attempt proof   BLOCKED_BY_P0_A
P0-F six-story native set         BLOCKED_BY_P0_A
D0 activation                     BLOCKED
```

## Reopen condition

A new native image generation for P0-A is authorized only after one route in `contracts/d0-p0a-route-matrix.json` evaluates READY. That requires all seven positive capabilities to coexist and every prohibited dependency to remain false.

Acceptable product changes include:

- Scheduled task-run results become programmatically accessible with generated image/file references;
- the Images tab gains a supported unattended file-access action;
- native image generation exposes an explicit caller-supplied story prompt/sub-context plus post-generation tools outside that generator context;
- ChatGPT exposes an unattended create-new-chat/Temporary-Chat primitive with connected tools and exact generated-file handoff;
- GPTs gain supported Scheduled invocation without losing fresh-conversation isolation.

Until then, further image generations do not increase confidence and are forbidden by the no-rework gate.
