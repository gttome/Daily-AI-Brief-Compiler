# Daily Compiler Architecture

## Mission

One substantial semantic producer creates one immutable edition bundle; GitHub performs deterministic validation/build/deploy/verification afterward.

## Six coarse stages

1. EDITORIAL — research, evidence, selection
2. CONTENT — stories, media, Watchlist, book mappings
3. IMAGES — six story-specific image operations
4. BUNDLE — immutable complete edition package
5. COMPILE — deterministic GitHub validation/build/deploy
6. VERIFY — deterministic preview verification

Stages 1–4 are semantic producer work. Stages 5–6 are GitHub-only.

## D0 Native Image Capsules

D0 is the intended permanent reader-story image architecture. Until the live P0-A through P0-F capability proof passes, D0 remains proof-gated and the already-published historical reader remains untouched.

```text
locked six-story edition
  -> six-image composition reservation plan
  -> Image Packet v3 per story
  -> proven fresh story-only native capsule
  -> built-in ChatGPT image generation
  -> same-invocation exact raw byte capture
  -> immutable Git persistence
  -> deterministic 1200x630 contain normalization
  -> exact persisted Visual Review v3
  -> six-image Set Review v3
  -> atomic ACCEPTED_LOCKED x6
  -> BUNDLE_READY
```

A D0 generator capsule receives exactly one generator-visible story projection. It receives no other story, prior image, benchmark image, run status, recovery prose, branch/path metadata, or orchestration context. "Ignore prior context" is not isolation evidence.

The capsule may end only after exact generated bytes are captured and durably persisted. If a fresh context or same-invocation exact-byte capture cannot be proven, D0 fails closed without a reader-story Proposal 1R fallback.

The deterministic GitHub layer owns normalization, structural checks, hashes, Git blob identities, compilation, deployment and live-byte verification. It performs zero model calls.

## Proposal 1R after D0

Proposal 1R remains in the repository for historical evidence, internal architecture diagrams, proof fixtures, developer documentation and deterministic diagram tests. After D0 activation it is not an automatic reader-story fallback.

## Deterministic compiler boundary

Once state is `BUNDLE_READY`, ChatGPT is no longer required. For D0 bundles, the compiler requires the atomic acceptance record, six accepted locked images, exact image/review/set-review identities, six unique byte streams and the fail-closed D0 image gate before building the reader.

## Complexity budget

- Primary semantic producer: 1
- Scheduled recovery invocations: max 3
- Supervisor: 0
- Watchdog Ring: 0
- Writer lease: 0
- Recovery lease: 0
- Worker pools: 0
- Runtime repair workflows: 0
- AI health polling: 0
- Major semantic stages: <= 6
- GitHub runtime workflows: <= 3
- Owner-liveness prompts: 0
- Work/Codex/paid API production dependencies: 0

If the architecture requires prohibited machinery, treat that as evidence against the Daily Compiler rather than expanding it.

## State and recovery

Each shadow edition uses one authoritative `shadow-runs/YYYY-MM-DD/compiler-state.json`. D0 attempt files are immutable authoritative image history. The coarse state records only the global image stage, set-plan identity, provisional individual passes and final atomic acceptance.

No leases, heartbeats, image worker pool, wake mechanism or micro-task orchestration state is permitted.

## Runtime repair policy

Active shadow executions do not repair program code. A software/platform defect preserves completed output and fails or blocks the run according to the contract. Development fixes happen outside the active shadow execution.
