# Independent current-contract image qualification packet

This is a bounded non-production qualification portfolio for the existing D1
image lane. It contains six real-source reference cases. It does not allocate
an edition, select October 9 stories or media, reopen a terminal run, reuse an
exhausted story target, or regenerate an accepted image. The `edition_date`
field is the qualification packet's required schema date, `2026-10-08`.

## Protected source binding

The six paraphrased source records were protected in
[PR 88](https://github.com/gttome/Daily-AI-Brief-Compiler/pull/88), merged as
`73b41c7312c9b1ad98fc33f455dc62cdc686476b`.
`source-records.json` and `eligibility.json` retain their original preparation
state; their then-unknown source commit is not rewritten. The separate
`source-evidence.json` and `request.json` bind the actual protected source commit.
Each story-content digest is the canonical JSON SHA-256 of its complete retained
story object in the source record. Source facts and conceptual visual geometry
remain separate.

source images are not published in this packet.

## Preparation result and execution boundary

The existing `admitD1Specifications` returned `PASS` for all six specifications
at `2026-10-08T16:41:57Z`. The plan has 72 individually supported components and
six distinct composition, layout, grammar, hierarchy and annotation signatures.
All component IDs participate in explicit relationships. Six exact prompts were
compiled with `compileD1StoryPrompt` and checked with `assertD1SubmittedPrompt`.
The hashes and counts are in `preparation-check.json` and `prompt-bindings.json`.
This establishes specification admission, not visible quality or live proof.

Run `node scripts/verify-value-image-request.mjs` from the repository root to
recheck the actual retained packet. It verifies the protected source projection,
current admission, exact prompt bytes, component relationships and initial
state, then writes `build/value-image-qualification/receipt.json`. That check
preserves this initial preparation scaffold; subsequent bound runtime state
belongs on the separate qualification branch and in its actual evidence snapshots.

The initial state is `PLANNED`, with zero native generations, no accepted assets
and no story contexts. It intentionally has no `specification_binding` yet.
The existing state function therefore returns `BLOCK_REQUEST_BINDING`.
`pending-request-binding.json` retains the unknown request storage commit as
null; placing a null commit inside the runtime binding would violate its schema.

After the request is protected, its actual immutable storage commit must be
bound separately from the already protected editorial-source commit. The
existing runtime branch planned by this packet is
`qualification/value-image-2026-10-08`. This record does not claim that branch
exists or that the existing image task has been armed. A valid initial binding
must include the exact request/source-evidence digests, source commit, request
commit, source-evidence path and complete attempt-log digest. Read back the
actual persisted target before any generation.

Only an exact compiled single-story prompt belongs in each fresh ordinary story
chat. Source records, source URLs, other story specifications, repository details,
proof history, orchestration instructions and benchmark source images stay out
of those generation contexts. The existing approved external Work runtime owns
browser orchestration and ingest. This implementation conversation generates
no images and supplies no runtime or pixel observations.

## Actual evidence still required

`evidence-plan.json` is a path plan with unknown values, not a qualification
companion or a set of PASS receipts. The actual executor must create the
current records described in `docs/D1-QUALIFICATION-EVIDENCE.md` and validated by
`image-studio/proof-evidence.mjs`. `ingest-mapping.json` defines the six intended
canonical PNG destinations; none of those images exists at preparation time.

The required resume observation is substantive. After exactly two images are
accepted and their original attempts retained, persist the actual
`BROWSER_RUNNING` state and attempt log at a commit, then interrupt the invocation.
A later invocation of the same existing task must preserve both accepted assets,
contexts and counts and continue with Story 3. Persist the later state and log
after its first actual generation is present but still pending review. The two
resume snapshots require distinct actual immutable commits, actual invocation
identities and actual timestamps. Their values must not be filled from a plan.

All native attempts count against the established four-attempt limit for their
own story. Accepted assets remain locked. Infrastructure or transport failure
resumes from the saved boundary and accepted bytes. R1, R2, R3, the one-image
capability proof and accepted October 7/8 outputs retain their original identities.

Complete canonical pixel reviews, permitted normalization, exact Git binary
readbacks and actual six-image set differentiation are still required. Build the
cloud proof only after every companion record exists and the existing validator
accepts it. Protected activation, existing-task readiness and release admission
remain separate proof-dependent operations. Current preparation reports live
proof `NOT_RUN` and activation `NOT_APPLIED`.
